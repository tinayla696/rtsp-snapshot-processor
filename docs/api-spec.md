# 外部API仕様

## 目的

外部端末から配信された RTP/RTSP ストリームを受信し、周期的に生成したスナップショットの保存情報を DB 管理サーバーへ通知するためのテスト用 API 仕様です。

本仕様の送信元は `rtsp-snapshot-processor`、受信側は DB 管理サーバーを想定します。

映像入力のネットワーク構成とは独立しています。実機のRTP配信は、同一LAN上にあるDocker実行ホストのLAN IPへ送信し、スナップショット処理後の通知だけをDB管理サーバーのHTTP APIへ送ります。

## 通知タイミング

- 最新フレームを設定された周期で JPEG 保存します。
- JPEG の保存に成功した場合だけ、DB 管理サーバーへ通知します。
- JPEG の保存に失敗した場合は通知しません。送信元のローカル SQLite には `status = 0` の記録を残します。
- 通知はスナップショット 1 件につき 1 回です。
- 現行実装では通知失敗時の自動再送は行いません。API は同じ通知を重複受信しても処理できるようにしてください。

## エンドポイント

| 項目 | 仕様 |
| --- | --- |
| HTTP メソッド | `POST` |
| パス | `/notify` |
| Content-Type | `application/json` |
| 文字コード | UTF-8 |
| 成功応答 | HTTP `200 OK` |
| 失敗応答 | HTTP `4xx` または `5xx` |

URL のホスト、ポート、スキームは送信元の `notification_url` 設定で指定します。

例:

```text
http://db-server.example.local:8000/notify
```

## リクエスト

### JSON スキーマ

```json
{
  "file_path": "string",
  "timestamp": "string"
}
```

### 例

```json
{
  "file_path": "/data/snapshots/snapshot_20260820_123456_789.jpg",
  "timestamp": "2026-08-20 12:34:56.789"
}
```

### 項目定義

| 項目 | JSON 型 | 必須 | 内容 |
| --- | --- | --- | --- |
| `file_path` | string | 必須 | 送信元で保存した JPEG の絶対パス |
| `timestamp` | string | 必須 | JPEG 保存時刻。形式は `YYYY-MM-DD HH:MM:SS.SSS` |

## 応答

DB 管理サーバーは、通知を受け付けて DB への登録が完了した場合、HTTP `200 OK` を返してください。

応答本文は送信元では利用しないため、テスト時は次の JSON を推奨します。

```json
{
  "status": "ok"
}
```

入力不備の場合は `400 Bad Request`、一時的な DB またはサーバー障害の場合は `500 Internal Server Error` などの `4xx` / `5xx` を返してください。

## DB 登録時の注意

`file_path` はスナップショット処理コンテナまたは実機上のパスです。DB 管理サーバーから画像ファイルを直接参照する場合、両システムで同じ共有ストレージをマウントし、同一パスとして見えるようにしてください。

共有ストレージを使わない場合、`file_path` は送信元内部のパスであり、DB 管理サーバーからファイルを取得できる URL ではありません。画像本体の転送や公開 URL が必要な場合は、別 API として定義してください。

## 時刻の扱い

現行実装の `timestamp` はタイムゾーンを含まない送信元ローカル時刻です。DB 管理サーバー側では、送信元のタイムゾーンをあらかじめ設定し、文字列を日時型へ変換して保存してください。

異なるタイムゾーンの実機を混在させる場合は、運用開始前に UTC の ISO 8601 形式（例: `2026-08-20T03:34:56.789Z`）へ変更するか、送信元のタイムゾーンまたは端末 ID を追加する必要があります。これは現行実装との互換性に影響するため、別途合意してください。

## セキュリティと運用

- 現行実装では認証ヘッダー、TLS、署名検証は行いません。
- 本番ネットワークへ公開する場合は、HTTPS、送信元制限、または API キー等の認証方式を追加してください。
- 同じスナップショットの再送を識別する ID は現行 payload にありません。重複排除が必要な場合は、`file_path` と `timestamp` の組み合わせを暫定キーとして扱うか、`snapshot_id` の追加を合意してください。

## テスト用サーバー

Docker Compose の `test-api` サービスがこの契約の受信サーバーです。

- ヘルスチェック: `GET /health`
- 通知受信: `POST /notify`
- 受信 payload のログ: `NOTIFY_LOG_PATH` で指定したファイル

起動:

```bash
docker compose up --build
```

テスト用 API は受信した JSON を検証し、ログへ記録して HTTP `200 OK` を返します。ログはComposeのボリューム経由で `docker-data/test-api/notifications.log` から確認できます。DB 管理サーバーへ置き換える際は、`/notify` の受信後に `file_path` と `timestamp` を検証して DB へ登録してください。
